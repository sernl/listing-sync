# Teachouse 0.14.0

## Landing

- The home page's Import, Distribute and Manage icons are redrawn as one clean set, and the Resources screenshot now has a full-width section of its own showing sample resources with their covers.
- The app card says what the app is for in one sentence and "Download the app once you’re signed in", with no download link on the public page; Windows and Android are easier to spot, and it says plainly that there is no iPhone or Mac app yet.
- The welcome, password-reset and password-changed emails use the Teachouse colours and fonts (Indigo and Teal, Poppins and Inter) under the Teachouse wordmark, on a light background that stays readable in dark-mode mail apps.

## Marketplaces

The Marketplaces page reads top to bottom in the order a seller does it.

- **Step 1, Get the app.** One sentence says why the app is needed: it signs in to TPT and TES on the seller's own device, so Teachouse never holds their passwords. The longer answer sits behind "Why you need the app". The Windows and Android downloads are right there, and the page says plainly that there is no iPhone or Mac app yet.
- **Step 2, Connect your shops.** Each shop's button says **Connect**. In the app it starts the sign-in; in a browser it scrolls back to step 1 with one line: "Open the Teachouse app on your device to connect." A shop that is already connected offers no button, because there is nothing to do. A shop connected on this device offers **Sign in again**.
- **Step 3, Who made this work.** The copyright declaration, unchanged. The warning banner that used to sit at the top of the page is gone; step 3 stays unticked until TPT's declaration is made.
- The page header offers **Get the app** in a browser and **Install on another device** in the app.

Everywhere a seller reads it, "machine" is now **device**: Settings shows **Device sign-ins** (anchor `/settings#devices`; old `#machines` links still land there), the Catalogue page is **Your devices' files**, and toasts, prompts, guides, API route summaries and the app's own error sentences say device. API paths, Rust identifiers and database columns are unchanged.

## Rich text

A resource's description is written in rich text or in Markdown, the seller's choice per resource.

- New resources start in rich text: a box with Bold, Italic, bulleted and numbered lists and Link buttons (Ctrl+B and Ctrl+I work too). Existing resources open in the format they are stored in. A "Which?" note explains the two.
- Switching converts what is written: Markdown to HTML by the same CommonMark rules the TPT projection uses, HTML back to the Markdown the toolbar writes. If the other format cannot hold something (a heading, a table, a picture), the console asks before switching.
- Rich text keeps eight elements and nothing else: paragraphs, line breaks, bold, italic, both kinds of list and web or mail links. A paste is reduced to those as it lands. The API applies the same allow-list when a changed HTML body is written (`crates/tam-api/src/rich_text.rs`), so a request that skipped the console stores nothing else either. An HTML body imported from a marketplace keeps its own markup until the seller edits it here, and the editor says what it cannot show.
- The character counter counts what a reader sees, not the tags.
- "What each marketplace shows" draws the description as each will carry it: TPT's as formatted HTML (with the markup one press away), Tes's as the plain text that will be posted.
- Tes's plain text now numbers a numbered list ("1.", "2.") rather than giving every item a dash, and a list nested in an item no longer leaves a blank line inside the list.
- A template's description stays Markdown. Applied to a rich-text resource, it arrives rendered rather than as literal asterisks, in the console and in the server's apply alike.

## Tutorial

A new account is shown around the console the first time it signs in. The screen dims, one part of the console is lit at a time, and a card says what that part is for in one sentence, with Next, Back and Skip. The tour covers Import, Catalogue, New resource (what a resource is), Automate, Marketplaces (get the app, then connect), and Billing under Account. It ends on "Start here", whose button opens a new resource.

- The tour runs on a computer and on a phone. On a phone the card sits along the bottom edge, and it moves above the tab bar when the lit item is on the bar. Arrow keys step through it, Escape skips it, and Tab stays inside the card. With reduced motion turned on, the spotlight jumps from item to item without sliding.
- Completing or skipping the tour is saved to the user, and it is not offered again. **Show me around** on Help and guides starts it again from the first step.
- Accounts made before this release are not interrupted. They see the tour once, on their first visit after buying a plan, unless they have already completed or skipped it.
- An operator impersonating a user never sees the tour offered. If the operator starts it from Help, nothing is saved for the user.

### Under the hood

- Migration `0088_onboarding.sql` adds `app_user.tour_state` (`due` | `predates` | `completed` | `skipped`) and `tour_settled_at`. Existing rows become `predates` and new rows `due`.
- `GET /v1/profile` now includes `tour: { state, settled_at }`. `POST /v1/onboarding/tour` takes `{ "outcome": "completed" | "skipped" }`, records it at the server's time, and returns the profile.
- In the console, `web/src/lib/tour/` holds the step model, the rule that decides when to offer the tour, and the placement helper, plus `Tour.svelte`, which is a native modal `<dialog>`. Each step's element is found by its `data-tour` key.

### Upgrading

Server, then console. Run the migration before the server starts.

## Billing

"Plan and moves" is now **Billing**, at `/settings/billing`. The old address still works and forwards there, including the `?checkout=` Stripe adds on the way back.

- The top of the page shows the plan you hold in its own colour, with what it gives you in one line and when it renews. **Adjust plan** takes you to the plans further down.
- **Payment** shows the card you pay with (brand and last four digits). **Update** opens Stripe's own card page and brings you back.
- **Invoices** lists your recent bills with the date, total, status and a **View** link to Stripe's invoice page, where you can download a PDF.
- **Cancellation**: **Cancel plan** asks you to confirm, then stops the plan from renewing. You keep the plan until the end of the period you paid for, and the page tells you that date. **Keep my plan** undoes it until then. A cancellation made in Stripe's portal shows up here too.
- After a checkout, the banner now says your moves are on the card **below**, which is where they are.

### Under the hood

- Migration `0089_billing_invoices.sql` adds `billing_subscription.cancel_at_period_end` (default `false`). The `customer.subscription.updated` webhook records it, and treats a scheduled `cancel_at` as a cancellation too. An invoice or checkout event leaves the stored value alone, so an invoice can't quietly renew a plan the seller cancelled. A new subscription starts with it cleared.
- `GET /v1/billing` adds `cancel_at_period_end` and `ends_at`. While the plan runs, the response has either `renews_at` or `ends_at`, never both.
- New routes: `GET /v1/billing/invoices` (read from Stripe on each request, drafts left out, nothing stored), `GET /v1/billing/payment-method` (the subscription's card, or the customer's default card if the subscription has none), `POST /v1/billing/payment-method` (a Billing Portal session with `flow_data[type]=payment_method_update`), and `POST /v1/billing/cancel` and `POST /v1/billing/resume` (`cancel_at_period_end` on the Stripe subscription; each returns the updated billing read).
- Checkout and the portal now send the browser back to `/settings/billing`. The landing page's links to `/settings/subscription` get forwarded there.

### Upgrading

Server, then console. Run the migration before the server starts. In the Stripe dashboard, the Billing Portal needs **payment method update** turned on (Account → Billing → Customer portal) for **Update** to open.
## Tiers

Teachouse now sells three subscription plans above the free one, each with a monthly and a yearly price. The founding offer and the paid "Move with me" session are no longer sold.

| Plan | Monthly | Yearly | Moves |
|---|---|---|---|
| Look | Free | Free | 5, once |
| Starter | $12 | $96 | 10 a month |
| Sync | $29 | $240 | 25 a month |
| Studio | $59 | $480 | 100 a month |

- Sync is unchanged. Existing Sync subscribers keep their plan, their price and their moves.
- Starter is new. It keeps edits in step once a day and includes scheduling, 5 templates and 5 collections. Statistics and automatic publishing rules start at Sync.
- Studio is now on sale. It includes 100 moves a month, hourly updates, unlimited templates and collections, and priority support.
- Move Packs are unchanged and can be bought on any plan.
- The pricing page and the console's Billing page show four plan cards. The Billing page has a monthly/yearly switch and marks the plan you are on. Someone who already pays changes plan from **Manage billing**.
- Plan card wording follows the founder's review. The first lines are "Import from wherever you sell" and "Edit once, sync everywhere", every card has "Add a watermarked preview of your file", AI reads "AI description fill, coming soon", and the free plan's trial moves are listed last. The labels are lowercase: (trial), (subscription), (one-off).

### Under the hood

- `tam-limits`: `Plan` gains `starter` (strength between Free and Sync). `PriceKey` is now `starter_{monthly,yearly}`, `sync_{monthly,yearly}`, `studio_{monthly,yearly}` and `pack_{20,50,100,250,500}`. `founding_yearly`, `move_with_me`, `FOUNDING` and `SERVICES` are gone. New: `PriceKey::plan()` and `PriceKey::list_cents()`. `PlanRow` carries `monthly_key`/`yearly_key` and drops `sold`.
- `GET /v1/plans` no longer returns `services` or `founding`. `GET /v1/billing` no longer returns `founding`.
- Checkout grants the plan the price key sells. A price change on a live subscription (a switch in the Stripe portal) revokes the old grant and writes one for the new plan under the same subscription. The moves accrued each period follow the plan held. A second recurring checkout beside a live subscription is refused with 409.
- Migration `0090_tiers.sql` widens `entitlement_grant_plan_known` to include `starter`. The `founding` move-ledger source and the `service_booking` table stay as history, and no new rows are written to either.
- Before deploying, create the Starter and Studio prices in Stripe and add them to the price map. Remove `founding_yearly` and `move_with_me` from the map: a key the build does not know stops the server at startup. Enable plan switching in the Stripe billing portal for the three products. Full list: `docs/notes/design/research/2026-09-27-subscription-tiers.md` §7.

## Discounts

Sales, one-off discounts and discount codes, run from a new admin **Pricing** page. Each one is a Stripe coupon the page creates when you save it; a code is also a Stripe promotion code.

### What sellers see

- **During a sale**, the landing pricing section and the console's Billing page strike the list price of every plan and show the sale price beside it, with the sale's banner above the plans ("Halloween sale: 25% off every plan until 31 October"). Any plan checkout applies the sale by itself. Packs are never on sale.
- **One-off discounts** are applied by themselves to the prices they name while they run, with no banner.
- **Discount codes** are typed on the Billing page before checkout ("Have a code?"). A code that does not reach the chosen price is refused on our page with one sentence. When no sale or code applies, Stripe's own checkout page also shows its "Add promotion code" field, and our codes work there too, limited in Stripe to the products they cover.
- If more than one automatic discount applies, the checkout takes the one that saves the seller most.

### How it works

- `GET /v1/plans` gains `sale: {percent_off, until, banner, banner_href} | null` (the sale open now) and is cacheable for 60 seconds.
- `POST /v1/billing/checkout` accepts an optional `code`. The session opens with `discounts[0][promotion_code]` for a valid code, else `discounts[0][coupon]` for the best open sale or one-off discount, else `allow_promotion_codes=true`; Stripe refuses a session with both.
- Admin routes (operator only): `GET /v1/admin/pricing`, `POST /v1/admin/pricing/sales`, `POST /v1/admin/pricing/discounts`, `POST /v1/admin/pricing/codes`, `POST /v1/admin/pricing/{id}/end`.
- Migration `0091_discounts.sql` adds `discount` (kind `sale`/`one_off`/`code`, terms, UTC window, Stripe coupon id) and `discount_code` (code, Stripe promotion code id). A sale's banner and theme are stored in `site_setting` under `sale.<discount id>`.
- Terms cannot be edited after saving, because Stripe coupons cannot be. To change one, end it and create a new one. Ending deletes the coupon and deactivates its codes in Stripe; subscriptions that already had the discount keep it.
- Windows are whole days in UTC: the first day starts at 00:00 UTC and the last day ends at 24:00 UTC. The coupon's `redeem_by` (and a code's `expires_at`) is the last second of the last day.
- A sale or discount covers the first payment by default (`duration=once`: the first month of a monthly plan, the first year of a yearly plan), or a number of monthly invoices (`repeating`).

### Seeding the October Halloween sale

Create it as data through the admin page (Pricing → New → Sale: name "Halloween 2026", 25 percent, 2026-10-01 to 2026-10-31, the banner below, theme Halloween), or with the same request the page sends, as an operator session:

```
POST /v1/admin/pricing/sales
Content-Type: application/json
Cookie: tam_session=<operator session>

{"name":"Halloween 2026","percent_off":25,"from":"2026-10-01","until":"2026-10-31",
 "banner":"Halloween sale: 25% off every plan until 31 October","theme":"halloween"}
```

It answers `201` with the stored sale, including its `stripe_coupon_id` (`teachouse-<uuid>`). SiteOps' Halloween theme is set separately (`PATCH /v1/admin/site`); tying the sale to the theme only records the link.

### Stripe

- Created by the admin page, per saved discount: one Coupon (`id=teachouse-<discount uuid>`, `percent_off` or `amount_off`+`currency=usd`, `duration`, `redeem_by`; for codes also `applies_to[products][]`). Per code: one Promotion Code (created under `Stripe-Version: 2025-09-30.clover`, `promotion[type]=coupon`). Nothing needs creating by hand before deploy.
- The Stripe key needs write access to Coupons and Promotion Codes and read access to Prices (a restricted key must be widened).
- Webhooks: none new are required.
- After switching Stripe accounts (test to live), the Pricing page flags any running discount whose coupon the new account does not hold ("Missing in Stripe"). End it and create it again.

## ResourceEdit

A resource can be edited at any time, and a reopened resource's own PDF is where its preview is made.

- **A live Tes listing no longer locks the resource.** `PATCH /v1/products/{id}` and the file add, replace and remove routes used to refuse the whole change with 422 `uncaptured_transition` when the resource had a live, bound Tes listing, and the console greyed out every field under "This resource is live, so you can't edit it here". The change is now always saved. The answer names where it goes: `reaches` lists the marketplaces the next send revises, and the new `kept: [{inventory, capability, reason}]` lists the live listings it cannot revise (today a live Tes listing: `tes.edit_published` is still uncaptured), which keep the copy they have. The console shows one info line ("TES (Tes.com) keeps the copy it has for now.") with a Why? behind it. Sending to that Tes listing is still refused at the send, exactly as before; TPT gets the change as a revise. Applying a template to resources no longer blocks the rows with a live Tes listing either. The `uncaptured_transition` error code is gone from the vocabulary.
- **Files read back.** New `GET /v1/products/{product}/files/{file}/content` answers the bytes of one of the resource's own files to a member of the owning organisation (another organisation, or a file id under the wrong resource, answers 404), with the stored content type, `Content-Disposition: inline` carrying the seller's file name, and `Cache-Control: private, no-store`.
- **Previews on a reopened resource.** On a saved resource, "Make a preview from your file" and "Change" read the first PDF from Teachouse when nothing closer is here (a PDF chosen in this session, or one the desktop app keeps), so a reopened draft or live resource can make, change and view watermarked previews in any browser. A PDF added or swapped in the Files panel feeds the maker straight away. View works for every stored file and preview.
- **New resource page.** The "start from a template" picker is an optional step 0 inside the flow, below the steps bar, with the flow's own spacing: a quiet dashed card that turns to the accent once a template is chosen, with a "How it works" explainer.

### Upgrading

Server and console together: the console reads `kept` from the edit and file answers.

## Admin

- **Users** is a compact, searchable list with status chips (unverified, banned, operator, no platform account); a row opens a side sheet (a bottom sheet on a phone) holding every action: ban, role, impersonate, sessions, grant a plan, and **delete** behind a typed-email confirmation.
- **Delete a user**: `DELETE /v1/admin/users/{auth_subject}` erases the platform user and the organisation that was theirs alone (migration 0092), and better-auth removes the identity (recorded as `user_removed` in `auth.auth_event`, `db/auth/0004`). Refused with a reason when the organisation has other members, the user is an operator, or Stripe holds a live subscription — cancel it first.
- **Guides** is a card grid (title, address, last update, published); the editor puts the text beside a live preview, with Edit / Preview tabs on a phone.
- **Impersonations** show name (email) for both parties, with the identity id on hover.
- **Request a marketplace** now emails every platform operator with a verified address (Resend, through the outbox drainer) with the requester, organisation and marketplace; the request row is kept. There is no backlog page.

## SiteOps

Operators get a Site page under Admin with three switches that change the whole site for everyone: maintenance mode, a seasonal theme on the public site, and a one-line banner.

### Maintenance mode

- While it is on, every page of the public site and every console page answers with a maintenance page: the brand mark, "We’re doing some maintenance", the operator's expected-back line, and a link to the status page.
- It is served by `tam-server` itself with HTTP 503 and `Retry-After: 3600`, so search engines keep the site indexed and come back later.
- Platform operators are not gated: a request carrying an operator's session sees the site as usual, so the person who switched it on can switch it off.
- Signing in (`/login`), password reset (`/reset`), the status page (`/status`), `/api/auth/*`, the API under `/v1`, the downloads directory and every asset stay reachable.
- The console checks the same switch at load, so a seller who signs in during maintenance is shown the notice instead of the console.
- `/maintenance/` is the operator's preview of the page with the current message; it answers 200.

### Seasonal theme

- Halloween (bats, ghosts, spider webs, pumpkins and a ghoul carrying books) or Christmas (snow, baubles, holly and a reindeer carrying books) decorate the public site between two UTC dates, both included, decided by the server's clock.
- The decorations sit in the page's empty corners and gutters, take no clicks, stay still for visitors who prefer reduced motion, and do not print.
- A striped ribbon along the header marks the season, and a small mark appears in the console's top bar.
- The public site reads the switch at load, so changing the theme needs no rebuild.
- `/?season=halloween` and `/?season=christmas` preview a theme whatever the dates say.

### Banner

- One line of text with a link, shown above the public site's header. The link is a path on this site or an https address.

### API

- `GET /v1/site` (public, `Cache-Control: public, max-age=60`) answers `{maintenance: {on, message}, theme: {name, from, until, active}, banner: {text, href} | null}`.
- `GET /v1/admin/site` answers the same view uncached, and `PATCH /v1/admin/site` changes any of the three, for platform operators only; everyone else gets the usual blank 401.
- Migration 0087 adds the global `site_setting` table (one jsonb value per key), which the discounts surface also uses for its `sale.*` keys.

### Setting the Halloween theme for October 2026

From Admin, Site: choose Halloween, from 2026-10-01 until 2026-10-31, and save. The same change over the API, with an operator's session cookie:

```
curl -X PATCH https://teachouse.io/v1/admin/site \
  -H 'content-type: application/json' \
  -b 'tam_session=<operator session>' \
  -d '{"theme": {"name": "halloween", "from": "2026-10-01", "until": "2026-10-31"}}'
```

### Upgrading

Server first: run migration 0087, then deploy `tam-server` with the new landing build (it now carries `maintenance/index.html`) and the console.
