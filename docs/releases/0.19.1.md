# Teachouse 0.19.1

Signing in is now rate-limited per real client instead of per Cloudflare data centre, and a cold page load makes under half the requests it did, with an 8 s watchdog that reloads a stalled first load and a package that warms the Cloudflare edge. Every answer carries security headers, the help guides open without signing in, and signing in takes you back to the page you asked for.

## Login performance

Signing in felt slow and was sometimes refused. The origin answers every API and sign-in request in under 100 ms, so this release fixes two problems in front of it: the sign-in rate limit grouped teachers by Cloudflare data centre instead of by teacher, and a first page load made so many small requests that a cold Cloudflare edge stalled on some of them.

- **Each teacher gets their own sign-in limit.** tam-auth now reads the client's address from `CF-Connecting-IP` first, then `X-Forwarded-For` (`auth/src/client-ip.ts`). Behind Cloudflare and Caddy, `X-Forwarded-For` holds the Cloudflare edge's address, so everyone routed through one edge shared one sign-in bucket (3 requests per 10 s) and got `429` together. better-auth had also logged "Rate limiting could not determine a client IP". The same address now goes into the session row and the audit row. Requests that never pass through Cloudflare (the dev server, the local stack) still use `X-Forwarded-For`. `CF-Connecting-IP` can be trusted only while the origin is reachable through Cloudflare alone.
- **Fewer, larger script files.** The console build now puts the modules every page loads together into one file each: the app shell, the console frame, and the pieces the sign-in screens share with the console, split by screen (`web/src/lib/chunk-groups.ts`, the `teachouse-chunk-groups` Vite plugin). Bytes barely move: `/login` gains 1.5 kB and `/resources` loses 1.5 kB. Lazy code (pdf.js, PostHog, the better-auth client) is still fetched only when needed, and the sign-in screen's preload list (`authPreloads`) still covers its own chunks only.

  Measured on the production build (`.vite/manifest.json`, every script and stylesheet the route waits for):

  | Route | Before: requests | Before: JS bytes | After: requests | After: JS bytes |
  | --- | --- | --- | --- | --- |
  | `/login` | 42 (39 JS, 3 CSS) | 148,483 | 12 (10 JS, 2 CSS) | 149,955 |
  | `/resources` | 97 (82 JS, 15 CSS) | 410,570 | 47 (35 JS, 12 CSS) | 409,099 |

  In Chromium, a cold load (cache disabled, against a local tam-server serving each build) counted every `/_app/immutable/` request the page made, including the ones the page asks for after it starts. Wire bytes are as tam-server sent them:

  | Route | Before: JS + CSS requests | Before: JS + CSS on the wire | After: JS + CSS requests | After: JS + CSS on the wire |
  | --- | --- | --- | --- | --- |
  | `/login` | 42 + 3 | 211 kB + 18 kB | 12 + 2 | 181 kB + 18 kB |
  | `/resources` | 84 + 15 | 505 kB + 134 kB | 37 + 12 | 460 kB + 132 kB |
  | `/templates` | 76 + 17 | 488 kB + 138 kB | 29 + 14 | 440 kB + 136 kB |

  The shell's own `modulepreload` list went from 18 files to 4, and the build writes 163 JS files instead of 211. Two other approaches were measured and rejected. Rollup's `experimentalMinChunkSize` (20 kB) brought `/resources` to 56 requests, but `/login` grew to 277 kB because it merged console code into the sign-in screen. Grouping `$lib/pages/<area>` by area cost `/resources` 37 JS files and 565 kB.
- **A stalled first load reloads once.** If SvelteKit has drawn nothing 8 s after the page opened, an inline watchdog in the shell reloads the page (`START_WATCHDOG` in `web/src/lib/lost-chunk.ts`). It shares the once-per-30-seconds guard with the existing lost-chunk reload, so a stall and a failed download together reload at most once per window. Before this, a request stuck on a cold edge waited for the browser's own timeout, 20–30 s in practice. The watchdog is only in built shells; `vite dev` is slower than 8 s on a cold start.
- **The edge can be warmed.** The new package `teachouse-edge-warm` (`nix/edge-warm.nix`, `nix/edge-warm.sh`) fetches every file under the console's `_app/immutable/` and the landing's `_astro/` through the public hosts: 16 at a time, GET only, to `/dev/null`, with an optional `--limit N`. It exits non-zero if any file answers other than `200`, or answers with HTML, which is what tam-server sends for a path it has no file for (the console shell). It prints how many came back as each `cf-cache-status`. The console and landing builds are inputs of the package, so it fetches exactly the files that are deployed. Cloudflare caches per data centre, so this warms the one the warming machine reaches. For a box in New Zealand, that is the one New Zealand teachers reach.

  `teachouse-edge-warm dash.teachouse.io teachouse.io` is the plain command line. `just edge-warm <console> <landing>` runs the same script against the local `web/build` and `apps/landing/dist`.

### Deploy

- No migrations.
- NixOS: `services.teachouse.warmEdge.enable = true;`. This adds `teachouse-edge-warm.service`, a oneshot that runs each time `tam-server.service` starts (so a deploy's new hashes are fetched at once), and `teachouse-edge-warm.timer` (`warmEdge.interval`, default every 15 minutes). The default `warmEdge.package` is built against the module's own `consolePackage` and `landingPackage`.
- Kubernetes: call `teachouse-edge-warm dash.teachouse.io teachouse.io` from the CronJob. Build it with `packages.teachouse-edge-warm.override { consolePackage = <the deployed console>; landingPackage = <the deployed landing>; }`. A console built with other arguments has other hashes, and the default package would then fetch files that are not deployed. The binary carries its own CA bundle.
- The edge must pass `CF-Connecting-IP` through to tam-auth. Caddy's `reverse_proxy` forwards request headers unless told to strip them.

## Launch hardening

- **Cloudflare Web Analytics reports again.** The edge injects its beacon into every page on both hosts, and both content-security policies refused the beacon's report, which logged an error in every visitor's browser console. `connect-src` on the landing policy (`serving.rs` `landing_policy`) and the console policy (`main.rs` `console_policy`) now names `https://cloudflareinsights.com` (`serving::BEACON_ENDPOINT`), and nothing else was added. The console policy also gains `frame-ancestors 'none'`, which the landing policy already had.
- **Security headers on every answer.** tam-server now sends `Strict-Transport-Security: max-age=31536000; includeSubDomains`, `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Permissions-Policy: camera=(), microphone=(), geolocation=()` and `Referrer-Policy: strict-origin-when-cross-origin` on every response from every tier, including the API, downloads and the maintenance page (`serving::transport_headers`, the outermost layer in `assemble`). Guide pages keep their stricter `Referrer-Policy: no-referrer`. Before this, only the CSP came from the origin.
- **Signing in returns you to the page you asked for.** A signed-out visit to a console address now goes to `/login?next=<path and query>` instead of a bare `/login`. Signing in lands on that page rather than on the home page. The login page also stores the destination in the sign-up intent, so a new account that returns through `/login` in the same browser goes there too. `safeNext` now asks the URL parser whether `next` stays on this origin, so `/\host` is refused along with `//host`.
- **The help guides are public.** `/guides` and every guide under it open without signing in (`PUBLIC_SECTIONS` in `web/src/lib/nav.ts`), and so the pricing page's FAQ links reach the guide they name. The API serves `GET /v1/guides`, `/v1/guides/_taxonomy`, `/v1/guides/{slug}` and `/v1/guides/images/{handle}` without a session. These routes return only published guides and their pictures, never drafts or organisation data. Every `/v1/admin/guides*` route still requires an operator session. A signed-out reader does not see "Show me around".
- **The marketing site has its own home-screen icon.** `apps/landing/public/apple-touch-icon.png` is the console's 180×180 icon, so `https://teachouse.io/apple-touch-icon.png` no longer redirects to dash. `nix/landing.nix` fails the build if the file is missing.

Deploy: no migrations and no new configuration. Before shipping, make sure nothing under `teachouse.io` is served over plain HTTP: `includeSubDomains` makes browsers refuse it for a year.
