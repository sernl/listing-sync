# Teachouse 0.16.0

## Seasons2

The marketing site has fourteen more seasonal themes, sixteen in all: New Year, Valentine's Day, St Patrick's Day, April Fools' Day, Easter, Matariki, Fourth of July, Back to school, Halloween, Guy Fawkes, Thanksgiving, Christmas, and Summer, Autumn, Winter and Spring.

- Each new theme has twelve hand-drawn stickers and a small mark for the console's top bar. For example, New Year has a clock holding books, a party popper, a cake and fireworks, with a skyline of Auckland, Sydney, London, New York and Tokyo along the top of the footer. Matariki has a kererū holding books, a ruru, tūī, a manu tukutuku kite, a hāngī and kete, harakeke, and the Matariki star cluster rising over hills at dawn.
- Every theme hangs a garland under the header and puts a striped ribbon along its lower edge. It tints the hero, dresses the top corners, and places stickers in the space above and under the hero art, beside the section headings and in the footer's corner. The ribbon and the tint use the site's palette, so they follow light and dark.
- A phone gets a lighter set: the ribbon, the garland, one small corner and the theme's character standing on the footer's edge.
- Stickers never sit over text or buttons and never take a click. Each theme has one small idle motion: a heart that beats, a snowflake that turns, a leaf that sways, a kite that sways. The motion is off for anyone whose device asks for reduced motion.
- The garland now belongs to the page rather than the sticky header, so it scrolls away instead of riding over the text.
- **Admin, Site:** the theme picker shows all sixteen themes with their console marks and when each usually runs. Each theme has its own Preview link, which opens the home page with `?season=<name>`.
- Preview any theme on any page with `?season=<name>`, for example `?season=new-year` or `?season=st-patricks`.

### Matariki: what the stickers draw on

The Matariki stickers use everyday motifs, not sacred ones. The motifs are the star cluster rising before dawn, kites, harakeke, the hāngī, kete, kūmara and native birds. There is no tā moko, whakairo, kōwhaiwhai, hei-tiki or Māori text. The nine-star cluster and what each star stands for follow Te Papa's [The stars of Matariki](https://www.tepapa.govt.nz/digital-museum/explore-digital-museum/matariki-maori-new-year/what-and-who-matariki/stars-matariki) and [Are there seven or nine stars?](https://www.tepapa.govt.nz/discover-collections/read-watch-play/maori/matariki-maori-new-year/matariki-star-cluster-are-there), which draw on Rangi Matamua's *Matariki: The Star of the Year* (Huia, 2017). Kites follow the NZASE [Manu tukutuku](https://nzase.org.nz/wp-content/uploads/2022/09/2022-09-Manu-tukutuku-NZASE-resource-1.pdf) resource: manu were flown to mark the start of Matariki.

## Feedback

- **Connecting TPT or TES works on Windows.** The app used to put the whole marketplace login in Windows Credential Manager, which refuses anything longer than 2560 characters, so connecting failed with "the session store refused: Attribute password encoded as UTF-16 is longer than platform limit of 2560 chars". Every platform now keeps the login sealed (XChaCha20-Poly1305) in a file in the app's own data folder, and the operating system's credential store holds only the 32-byte key that opens it. A login an earlier version kept in the credential store moves into the file the first time the app reads it, so nobody is signed out by the update.
- **The tour ends on getting the app.** In a browser, the last card is **Start here: download the app**, with a button to the Get-the-app step on Marketplaces. In the app it still ends on **Create your first resource**.
- **A short tour the first time you open the app.** Three cards on each new device: marketplaces are connected here, in the app; open Marketplaces and press Connect; importing, distributing and managing work in the app or in your browser. It is shown once per device.
- **Catalogue → Files.** The Catalogue tab "Your devices' files" is now called **Files**, in the navigation, the page title and the guides.

## PerfLogin

The sign-in, sign-up and password-reset pages now open in about a second on a slow connection, down from about three.

- The signed-out pages have their own light frame: none of the console's shell, query client, icon-heavy chrome, analytics or compiled rules load before the form, and nothing waits for the API before the first paint. Maintenance mode is checked right after that paint.
- Product analytics loads only after the page has finished loading and gone idle. On the signed-out pages it also waits for your first click or key press. The sign-in library loads when you submit.
- The fonts are content-hashed and cached for a year. The two used on the sign-in card are preloaded, and each sign-in page's own scripts are preloaded from the first byte, together with a connection to the security check.
- The PDF library behind the preview maker now loads only when you make a preview. The console's rules module now waits until the resource list has finished loading.

Measured with headless Chromium 153 on a cold cache, throttled to 1.5 Mbps down and 150 ms round trip. Each figure is the median of 5 runs. Prod is teachouse.io on 0.15.0. Local runs go through HTTP/2 with brotli, as prod does.

## AdminMail

Admins can now email sellers from **Admin → Mail**.

- **Write**: a subject and a body in the same editor the description uses, now with headings and pictures. A **Variables** menu drops in `@name`, `@first_name`, `@email`, `@org`, `@plan`, `@date`, `@link` (the brand button, pointing at an address you set for the email) and `@unsubscribe`. The preview beside it shows the email exactly as it will arrive, in the Teachouse wrapper, with sample values. **Send a test to yourself** mails you one copy.
- **Choose who gets it**: everyone, free (Look), paid, or one plan (Starter, Sync, Studio); admins left out by default; verified addresses only by default. The count shows before you send. Sellers who unsubscribed and accounts that never signed in are never included.
- **Send**: each seller gets their own copy, filled in with their own name, organisation and plan, sent at most ten a second. Each row records queued, sent (with the Resend id), failed (with Resend's answer) or skipped (unsubscribed, no address, or not verified).
- **Log**: every email with who sent it, when, to which filter, and how many were sent, failed or skipped. The detail view lists each seller's status, can try the failed ones again, and **Delete** removes the body and the per-seller rows to free space while keeping the log line and its counts.
- **Unsubscribe**: every email has an unsubscribe link in its footer and one-click unsubscribe headers for mail apps. Following it stops news from Teachouse and nothing else. Sellers can turn news back on (or off) under **Settings → Notifications**.

For the operator: campaigns go out from a second sender, `--marketing-email-from` (default `no-reply@marketing.teachouse.io`), which Resend must hold as a verified domain. Migration 0097 adds `mail_campaign`, `mail_campaign_recipient` (each row is that seller's outbox entry) and `mail_image`, and `app_user.marketing_opt_out` / `marketing_token`. Pictures uploaded for an email are served publicly at `/v1/mail/images/<hash>` so mail apps can load them; guide pictures stay behind sign-in.

## TierLimits

- **Every plan now has a resource limit except Studio.** Look includes 100 resources (it was 500), Starter 500, Sync 2,000, and Studio has no limit. Prices are unchanged.
- **Watermarked previews are counted each month.** Look makes 5 a month, Starter 50, Sync 200, and Studio has no limit. The count starts again on the 1st of each month (UTC). Every preview a resource gains counts, whether it is made in the preview maker or dropped in as a file. Deleting a preview does not give one back.
- **If you already have more than your plan's new limit, you keep everything (the grandfather rule).** Nothing is removed, hidden or locked: you can still open, edit, publish and delete what you have. You can't add more resources until you upgrade or delete enough to be under the limit. The same holds for labels, templates, collections and storage. Preview counts start at zero on the day this ships, so nobody starts the month already used up.
- **The limit applies everywhere a resource can arrive.** A new resource, a spreadsheet row, an import from your shop, a resource moved from a device, a re-import that brings a deleted resource back, and undoing a merge all stop at the limit. When an import reaches it, the resources that fit arrive, and each one after that is marked as not imported with the reason. The rest of the import still finishes.
- **Other limits are now checked on every path.** Labels created by a spreadsheet import count toward your plan's labels. Covers and pictures from a shop import count toward your storage: a picture that would go over it isn't kept, and the resource arrives without it. Statistics are collected only on plans that include them. A plan that syncs less often now takes effect on the next sync, not only after you save your sync settings again.
- **Billing shows what you have used:** resources, templates, collections, labels, devices, and this month's previews against your plan, plus the date previews start again.
- **One sentence for a full plan, everywhere.** The disabled New resource button, the create form, an import row that didn't arrive and the preview maker all say what your plan includes and what you can do, e.g. "Your plan includes 100 resources. Upgrade to add more." Billing marks a used-up allowance as "full".
- The pricing page and the plan cards show the new limits. They come from the same table the server enforces.

Deploy: migration 0098 (`usage_counter`) runs on start. No backfill is needed, because preview counts start at zero.

## FilesStreaming

**Files you import stay on your devices.** Teachouse no longer copies imported files to its servers. When you view a file, make a preview from it or download it in the console, Teachouse asks one of your devices that holds it for the file and passes it straight through to your browser without keeping it. Files you upload yourself in the console are still stored by Teachouse and are always available.

- **The copies 0.15.0 made are deleted.** Migration 0099 deletes every stored copy of an imported file. It deletes the database row that holds each copy's encryption key, so the encrypted object left in storage can never be opened again, and the store's own lifecycle removes it later. Uploads, thumbnails, avatars and anything an import still names are untouched. A copy no longer counts towards your plan's storage.
- **View, Preview and Download work through your device.** They need one of your devices that holds the file to be on, with the Teachouse app open. PDFs still open a few pages at a time (the browser asks for byte ranges, and Teachouse asks the device for just those bytes), so the first pages draw before the rest arrives. Large files are fetched from the device in parts of 32 MB.
- **When the device is off**, the console says "Your file is on <device>, which is offline. Open the Teachouse app there." and has an **Explain** link. A device counts as online for this while its app has checked with Teachouse in the last minute.
- **Your devices' files**: the **Where** column shows only device names, each with an online dot. Files you uploaded show **Uploaded**. The Teachouse/both states are gone.
- **Android** shows a notification, "Teachouse is sharing your files", while it can pass files on, including with the screen off. The phone stops sharing 10 minutes after you last used the app or it last passed on a file, which saves battery. After that, open the app to share again. Battery savers on some phones can stop it sooner.
- **The desktop app** answers file requests while it is running. It no longer copies files to Teachouse in the background.
- **Safety.** Each request to a device carries a single-use permission signed by Teachouse. It names the device, the file and the exact bytes, and expires after two minutes. The device refuses any request that doesn't match. Your marketplace logins and Teachouse sign-in never leave the device. Teachouse keeps only the request (which file, which bytes) until it is answered, and never the bytes themselves.
- **The online dot agrees with View.** The dot on **Your devices' files** and on a resource's files, and the Online/Offline filter, use the same test as View: the device's app asked Teachouse for file requests in the last minute. Before, a device counted as online for 10 minutes after its last check-in, so a device whose app had just stopped showed "Online now" while View said it was offline. Device-to-device copies still use the 10-minute check-in.
- **Android phones without a screen lock.** Teachouse keeps a phone's files under a key that Android only releases on an unlocked phone. A phone with no PIN, pattern, password or biometric lock has no unlock, so Android refuses the key, and the phone kept and served no files without saying why. The requirement stays, so the files stay protected. Now the app shows "Set a screen lock on this device to keep your files on it, then open Teachouse again." with an **Open settings** button that opens the phone's screen-lock settings. New desktop command `open_security_settings` (granted to the console).
- **Version.** The desktop and Android apps report 0.16.0.

Why: `docs/notes/design/research/2026-09-29-file-custody.md`.

Routes: removed `GET /v1/library/missing` and `PUT /v1/library/files/{hash}`. Added `GET /v1/devices/{device}/streams` (the device's long poll) and `POST /v1/devices/{device}/streams/{stream}` (the device's answer). `GET /v1/products/{p}/files/{f}/content` and `GET /v1/library/files/{hash}/content` pass imported files through from a device and take `?probe=1`. New error codes: `device_offline` (409, `detail.device`) and `streaming_unavailable` (503). `FileView.server_copy` is replaced by `custody` (`uploaded`, or `devices` with holders), and `LibraryFileView.server_copy` by `uploaded`.

Migration: `0099_device_streams.sql` adds `device.stream_polled_at` and the `device_stream` table (request metadata only, row-level security like every tenant table) and deletes the server copies.

What the migration deletes in production. `blob` has no column recording which path wrote a row, so a server copy is found by what refers to it. A `blob` row is deleted only when all of these hold:

- its digest is the `observed_hash` of an imported `product_file` in the same organisation. Imported means `hash IS NULL`: the row is marketplace-sourced, and the server never verified any bytes for it.
- no `product_file.hash` names it. Those are files the seller uploaded, so bytes the seller uploaded and also imported survive.
- no import batch row names it as its file or cover, and no import run item names it as its cover.
- no TPT thumbnail (`product_tpt_base.thumbnail_hashes`) and no video preview (`product_tpt_base.video_preview_hash`) names it. An import never writes either field, so both are uploads.
- no `app_user.avatar_hash` names it.

So the number of rows deleted is the number of distinct (organisation, digest) pairs in 0.15.0's server-copy ledger (`ServerCopyRepo`) that none of the references above protect. Run the same `SELECT count(*)` with this predicate against production before deploying if you want the figure. The encrypted objects stay in the store until its lifecycle removes them.

Deploy: tam-server runs as two replicas. A device's answer can reach either one, so each pod must know the address the other can reach it on. Add `TAM_POD_IP` from `status.podIP` (downward API) to the tam-server container, and add `--broker-advertise $(TAM_POD_IP):<serverPort>` to its args. Without that flag, an answer that lands on the other pod is refused and the viewer shows the device as offline. The pods must be able to reach each other on the server port, which the cluster network already allows. The broker signs requests with the entitlement key (`--entitlement-key-path`, already configured); a deployment without it answers `streaming_unavailable`. Ship the desktop and Android 0.16.0 builds with the server. Apps older than 0.16.0 don't answer file requests, so their files show as offline until they update.
