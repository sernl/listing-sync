# Adopting Bazel in listing-sync: cost, value, and verdict

Prepared 2026-09-03 against the tree at `/home/sernl/projects/edtech-workspace/listing-sync`.
Every URL was fetched 2026-09-03; where a page states its own measurement date, that date is given beside the claim.
Repository facts marked "measured" were derived by reading or counting files in the tree on 2026-09-03; the command is named where it is not obvious.
No build was run for this document, so no timing here is a fresh measurement of this workspace; the timings quoted are ones already recorded in `logs/`.

## Executive summary

1. Bazel would replace cargo for compilation only, never entirely: `cargo sqlx prepare`, `cargo-deny`, `cargo-audit`, `cargo tauri`, `cargo-xwin` and rust-analyzer's project model all stay, so the end state is two build systems, not one.
2. The Rust core is the part Bazel handles best: `crate_universe` ingests the existing `Cargo.toml` and `Cargo.lock` directly, and clippy, rustfmt, wasm-bindgen and per-crate tests all have documented rules.
3. The Rust core is also where the hidden work is: 20-plus `include_str!` sites become hand-listed `compile_data`, six `env!("CARGO_MANIFEST_DIR")` sites and three `env!("CARGO_TARGET_TMPDIR")` sites have no cargo to supply them, and the founder-gated `[workspace.lints]` table has no effect on a rustc invocation Bazel composes itself.
4. Tauri has no Bazel story: tauri-apps/tauri#12367 is open, and names three blockers, one of which is that Tauri writes absolute paths that a per-action sandbox invalidates.
5. `web/` uses npm, and rules_js is built around pnpm, so the web lane starts with a package-manager migration before any SvelteKit or vitest wiring.
6. NixOS is the awkward host: Bazel's C++ autodetection looks for `/usr/bin/gcc`, which does not exist here, so toolchains must come from `rules_nixpkgs` or an equivalent, and that layer is itself a 0.13.0 third-party dependency.
7. The genuine win is cross-lane deduplication, not raw speed: `just check`, `just check-portable` and `nix flake check` today compile overlapping work into three separate caches, and one Bazel cache would collapse that.
8. The genuine loss is the inner loop: Bazel does not use rustc's incremental compilation (bazelbuild/rules_rust#684 is still open, blocked on sandboxing), so an edit inside a crate recompiles that whole crate where cargo would not.
9. Estimate for this repository: 31 to 60 engineer-days excluding the Tauri bundle, plus a permanent upgrade tax against a 0.x rule set that shipped six minor releases in the last release window listed on its releases page.
10. Verdict: reject for now; the four cheap measures in section 5 attack the same pains for well under two engineer-days, and the trigger to revisit is a second engineer plus real CI, not a faster laptop.

## 1. What Bazel would have to cover here, and how each piece stands today

The workspace is 30 cargo packages (measured, `cargo metadata --no-deps`), 226 Rust files and 102,985 lines under `crates/` and `apps/` (measured, `find` plus `wc -l`), and a `Cargo.lock` holding 687 package entries (measured, `grep -c '^\[\[package\]\]'`), so roughly 657 external packages once the workspace members are subtracted.
That is larger than the "about 430" in the brief, and the difference matters only for the `crate_universe` step, which scales with the lock rather than with our source.

### rules_rust and crate_universe

rules_rust is at 0.74.0, dated 28 August on its releases page, and the ten most recent entries run from 0.68.1 to 0.74.0, so it remains a pre-1.0 rule set with a fast minor cadence ([releases](https://github.com/bazelbuild/rules_rust/releases)).
Its own introduction states the project "aims to support Linux and macOS" and that "we do not have sufficient maintainer expertise to support Windows", and names Bazel 7.4.1 as the oldest tested version ([introduction](https://bazelbuild.github.io/rules_rust/index.html)).
`crate_universe` is the dependency bridge: `crate.from_cargo()` "can ingest a root Cargo.toml file and generate Bazel dependencies from there", build scripts are generated by default, and per-crate `crate.annotation()` entries carry `build_script_env`, `build_script_data`, `build_script_tools` and `build_script_use_cc_toolchain` for the crates that need them ([crate_universe with bzlmod](https://bazelbuild.github.io/rules_rust/crate_universe_bzlmod.html)).
Dependency resolution happens in a repository rule, so every change to a manifest needs an explicit repin: "CARGO_BAZEL_REPIN=1 bazel sync --only=crates" (same page).
That is a new step in the loop every time a `cargo add` lands.

The dependency graph contains 37 proc-macro or derive packages and 34 `-sys` packages (measured from `Cargo.lock`), including `webkit2gtk-sys`, `gtk-sys`, `soup3-sys`, `javascriptcore-rs-sys` and `libsqlite3-sys`.
The `-sys` crates are the ones that find their libraries through `pkg-config`, which the devshell currently satisfies with `pkgs.gtk3`, `pkgs.webkitgtk_4_1` and `pkgs.libsoup_3` in `buildInputs`.
Under Bazel each of those becomes an annotation that must be handed the same headers and `.pc` files as declared inputs, or the build script fails inside the sandbox.
`ring 0.17.14` and `cc 1.4.4` are present, so at least one C compile runs through `cargo_build_script` and the Bazel CC toolchain; `blake3 1.8.7` is in the lock but the justfile records that its `pure` feature was enabled by founder decision on 2026-09-03, which removed its `cc` and `ml64.exe` paths.

Only one first-party build script exists, `apps/desktop/src-tauri/build.rs`, and it is a direct sandbox conflict: it calls `std::fs::create_dir_all("../../../web/build")` before `tauri_build::build()`, which is a write outside its own package.
A Bazel action cannot do that, so the desktop crate needs the frontend output supplied as a declared input instead.

### sqlx

`tam-storage` holds all 182 `sqlx::query*!` macro sites (measured), backed by 174 files in `crates/tam-storage/.sqlx` and 44 migrations.
Offline compilation is exactly the mode a hermetic sandbox needs, and the sqlx docs describe the same constraint for docs.rs: supply a `.sqlx` directory and set `SQLX_OFFLINE` ([sqlx FAQ](https://docs.rs/crate/sqlx/latest/source/FAQ.md), [query macro docs](https://docs.rs/sqlx/latest/sqlx/macro.query.html)).
The wiring is therefore `.sqlx` as `compile_data` plus `SQLX_OFFLINE=true` in `rustc_env`, which is mechanical.
What does not go away is generation: launchbadge/sqlx#3555, "Running `sqlx prepare` without Cargo", was opened 2024-10-10 by a team in exactly our position ("we're using Bazel and rules_rust ... without Cargo at all") and is still open with no maintainer answer ([issue #3555](https://github.com/launchbadge/sqlx/issues/3555)).
So `just db-prepare` and `just db-verify` keep needing cargo and a live database no matter what Bazel does.

### Cargo environment variables that Bazel does not supply

Twenty-plus files use `include_str!` or `include_bytes!` (measured), and each becomes an explicit `compile_data` entry, because Bazel gives a rustc action only its declared inputs.
Six sites use `env!("CARGO_MANIFEST_DIR")` and three use `env!("CARGO_TARGET_TMPDIR")` (measured, in `tam-storage`, `tam-taxonomy` and their tests).
rules_rust has an open tracking issue for exactly this parity gap, "Set the same env vars as cargo both when invoking rustc and when invoking a cargo_build_script" ([issue #661](https://github.com/bazelbuild/rules_rust/issues/661)), and a companion report that `rust_doc` does not define `CARGO_MANIFEST_DIR` ([issue #947](https://github.com/bazelbuild/rules_rust/issues/947)).
`CARGO_TARGET_TMPDIR` has no Bazel analogue at all; those three tests would move to `TEST_TMPDIR`.

### Lints, clippy and rustfmt

rustfmt is well served: `bazel run @rules_rust//:rustfmt` formats, and `rustfmt_aspect` checks, with the config chosen by a build setting rather than by filesystem discovery, and the docs advise enabling the aspect only in CI "so formatting issues do not impact users' ability to rapidly iterate on changes" ([rustfmt](https://bazelbuild.github.io/rules_rust/rustfmt.html)).
Clippy has both `rust_clippy` targets and a `rust_clippy_aspect` ([rust_clippy](https://bazelbuild.github.io/rules_rust/rust_clippy.html)).
The enforcement layer is where this bites.
The root `Cargo.toml` carries a 78-line founder-gated `[workspace.lints]` table, and that table is a cargo feature: cargo translates it into rustc flags.
Bazel composes its own rustc command line from BUILD files, so the table would have to be re-expressed as `rustc_flags` on every first-party target and kept in sync by hand, or the deny-set silently stops applying (see the unverified list).
The same question applies to `clippy.toml`, which the flake already guards with two checks (`ban-strings` and `clippy-toml-count`) and which `crates/ban-probe` exists to exercise.

### Cross-compilation, wasm, and tests

`rust-toolchain.toml` pins 1.97.1 and five extra targets, and `just check-portable` compiles two crate sets against each.
rules_rust supports extra target triples through its toolchain extension, but the Windows leg runs into the maintainers' own statement above, and the Apple legs need an SDK story that cargo currently sidesteps because `cargo check` never links.
wasm is the cleanest piece: `rust_wasm_bindgen` "generates javascript and typescript bindings for a webassembly module using wasm-bindgen", with `target` selecting the output flavour and a custom `rust_wasm_bindgen_toolchain` overriding the bundled CLI version ([rust_wasm_bindgen](https://bazelbuild.github.io/rules_rust/rust_wasm_bindgen.html)).
That override is required here, because `crates/tam-core-wasm` pins wasm-bindgen 0.2.121 to match the nixpkgs CLI, and the CLI refuses a mismatched crate version.
There is no nextest rule; Bazel's unit is a `rust_test` target per crate, cached by input hash, which is a different shape from `cargo nextest run` but covers the same ground for the non-database suites.

### Tauri

Tauri under Bazel is unsupported and known to be unsupported.
tauri-apps/tauri#12367, "[feat] Support non-cargo build systems (e.g. bazel)", opened 2025-01-12, is open and unassigned, and names three obstacles: the CLI invokes cargo; "the lists of permissions files created by tauri use absolute paths, which doesn't work with Bazel since the sandbox path changes for each action"; and `tauri bundle` "looks for the app in a fixed cargo-specific location" ([issue #12367](https://github.com/tauri-apps/tauri/issues/12367)).
The practical answer is the one the flake already takes for a different reason: exclude `tam-desktop` and keep `just desktop-build` and `just desktop-build-windows` on cargo.

### Web

`web/package.json` is npm with a `package-lock.json` workflow (`npm ci` in `just web-check`).
rules_js "mimics pnpm to lay out a node_modules tree" and mirrors "pnpm's lock file into starlark code" ([rules_js](https://github.com/aspect-build/rules_js)); the Aspect documentation site now sits behind a login, so the npm and yarn conversion path could not be read directly and is listed as unverified.
Migrating `web/` and `auth/` to pnpm is therefore step zero, before SvelteKit's `vite build`, `svelte-check` and `vitest` are each wrapped as Bazel targets.
One part of the web lane improves under Bazel: the `vocab.ts` freshness diff and the `web-wasm` dependency are currently sequencing enforced by a recipe, and both are naturally expressed as graph edges.

### Nix interplay

Bazel's stock C++ autoconfiguration searches `/usr/bin/gcc` and friends, which do not exist on NixOS, and the failure recurs inside the sandbox even when a compiler is found on `PATH` ([nixpkgs#44105](https://github.com/NixOS/nixpkgs/issues/44105), [nixpkgs#38471](https://github.com/NixOS/nixpkgs/issues/38471)).
The standard remedy is `rules_nixpkgs`, which exists to "import external dependencies (like system packages) into Bazel hermetically", with bzlmod examples pinned at 0.13.0 and a documented `--host_platform=@rules_nixpkgs_core//platforms:host` requirement ([rules_nixpkgs](https://github.com/tweag/rules_nixpkgs)).
It also documents a bzlmod-specific hazard, that external-workspace labels "will resolve to paths that contain ~ characters" which Nix path literals reject.
Adopting Bazel here therefore means adding a Nix-to-Bazel bridge on top of the flake, not removing the flake.

### jj colocation

No conflict is expected, and none was found: Bazel reads the working tree and keeps its output base under `~/.cache/bazel`, outside the repository.
One concrete action is required, because the root `.gitignore` carries no `bazel-*` entry (measured): the `bazel-out`, `bazel-bin`, `bazel-testlogs` and `bazel-<workspace>` convenience symlinks Bazel creates in the workspace root must be ignored, or they become untracked unignored files in a jj working copy, which is the hazard the fleet rules already name.

## 2. What actually gets faster, and what does not

Bazel's caching is per action, keyed on the action's declared inputs, split between an action cache "of action hashes to action result metadata" and a content-addressable store of outputs, reachable over HTTP, gRPC, or a local `--disk_cache` directory that the documentation recommends "when switching branches and/or working on multiple workspaces of the same project" ([remote caching](https://bazel.build/remote/caching)).
Three consequences are real for this repository.

First, cross-lane deduplication.
`just check` compiles into `target/`, `nix flake check` compiles inside crane's sandbox, and `just check-portable` compiles five more target triples locally; the flake's own `portable` check sets `cargoArtifacts = null` with the comment that "crane's host-target artifacts are not reusable across a --target".
One Bazel cache makes the second and third consumer of any identical action a cache fetch.
This is the strongest argument for Bazel here, and it is an argument about duplication rather than about compiler speed.

Second, concurrent agents.
Bazel does not remove serialization by itself: "Each server can handle at most one invocation at a time; further concurrent invocations will either block or fail-fast", and the server is chosen by output base ([client-server](https://bazel.build/run/client-server)).
Agents would each need their own output base, which is the exact analogue of giving each agent its own `CARGO_TARGET_DIR`.
The difference is that with a shared disk cache the second agent's duplicated actions become fetches instead of recompiles, whereas separate cargo target directories duplicate the compile outright unless sccache is added.

Third, the shared cache can extend beyond this machine.
BuildBuddy's free tier lists up to 10 users, "100 GB of cache transfer" and "up to 80 cores for remote builds" ([pricing](https://www.buildbuddy.io/pricing/)); bazel-remote is the self-hosted option, serving the REAPI action cache, CAS and capabilities services over HTTP/1.1 and gRPC with disk, S3, GCS or Azure backends ([bazel-remote](https://github.com/buchgr/bazel-remote)).
For a solo founder on one machine, the local `--disk_cache` is the part that pays; the remote tier pays when a second machine or a CI runner exists.

The honest limits are as follows.

rustc's unit of compilation is the crate, and Bazel does not drive rustc's incremental mode.
bazelbuild/rules_rust#684, "incremental compilation without a worker", is still open, because "rustc does not expect the source files to change location, and it will consistently crash when used in a sandboxed context", so the PR's approach was to disable sandboxing for incrementally compiled targets; a maintainer objected that "Bazel doesn't really have a concept of volatile files which are both inputs and outputs of the same action" and preferred proper worker support, which has not landed ([PR #684](https://github.com/bazelbuild/rules_rust/pull/684), [issue #412](https://github.com/bazelbuild/rules_rust/issues/412)).
So for the edit-compile-test loop inside one crate, Bazel is typically slower than cargo, not faster.

Hermeticity costs are paid first and paid always.
`just db-test` runs against a live Postgres on 127.0.0.1:5433, `npm ci` fetches, and `cargo deny check` reads a network advisory database; none of those is a cacheable hermetic action, so each must be tagged local or moved out of the graph, and Bazel's caching contributes nothing to them.
Those are also the slow lanes: the recorded nextest summaries in `logs/` show the non-database suite at 0.958 s for 839 tests and 0.476 s for 566 tests, against database lanes at 28.1 s, 89.8 s, 134.0 s and 193.0 s.
Test-result caching is a real Bazel feature, but here it would save the one second, not the three minutes.

## 3. Migration estimate

Assumptions: one engineer who already knows this repository and does not already know Bazel; bzlmod rather than WORKSPACE; `crate.from_cargo()` rather than vendoring; the Tauri bundle explicitly out of scope and left on cargo; days are focused engineer-days, not calendar days.

| Component | Days | Note |
|---|---|---|
| Bootstrap: MODULE.bazel, .bazelrc, toolchain 1.97.1 plus five extra triples | 1-2 | Mechanical, well documented |
| crate_universe over ~657 external packages, annotations for `-sys` and build-script crates | 3-6 | Risk concentrates in `ring` and the four GTK/WebKit `-sys` crates |
| BUILD files for 30 first-party crates: globs, `compile_data`, `rustc_env`, per-target feature sets | 5-8 | No cargo feature unification; each feature combination is explicit |
| sqlx offline wiring: `.sqlx` as data, `SQLX_OFFLINE`, 182 macro sites in one crate | 2-4 | Generation stays on cargo permanently (sqlx#3555) |
| wasm32 plus `rust_wasm_bindgen` with a toolchain pinned to CLI 0.2.121 | 1-2 | Version match with the crate is mandatory |
| Five client triples under platform toolchains | 4-10 | Windows MSVC is the stated weak spot; Apple SDK provisioning is unquantified |
| `web/` under rules_js: npm to pnpm, vite build, svelte-check, vitest | 5-10 | Package-manager migration precedes any rule work |
| NixOS toolchain interop via rules_nixpkgs or a nix-provided toolchain | 3-6 | New third-party layer at 0.13.0 |
| Disk cache plus one remote cache (bazel-remote or BuildBuddy) | 1-2 | Cheap once the graph builds |
| Re-expressing the gated lanes: purity as a `bazel query`, lints as `rustc_flags`, clippy and rustfmt aspects, `rust_test` in place of nextest | 3-5 | The founder-gated enforcement is the part that must not silently weaken |
| Stabilisation, deciding the fate of the flake checks, documentation | 3-5 | |
| Total | 31-60 | Tauri excluded; attempting it is open-ended |

The ongoing tax has three parts.
rules_rust upgrades: the releases page lists six minors between 0.68.1 and 0.74.0, each a potential break against a 0.x API.
Lockfile churn: every dependency change needs `CARGO_BAZEL_REPIN`, and a vendored setup would add a second lockfile, `Cargo.Bazel.lock`.
Dual maintenance: this is not a cutover.
cargo remains the only way to run `sqlx prepare`, `cargo-deny`, `cargo-audit`, `cargo tauri build` and `cargo-xwin`, so BUILD files and Cargo manifests both stay live and both must stay true, and every new crate is added twice.

## 4. Cheaper measures that attack the same pains

The pains named are lock contention between concurrent agents, slow builds, and a `target/` directory measured at 282,255,831,040 bytes, that is 263 GiB, by `diskus` on 2026-09-03.
There is currently no `.cargo/config.toml` in the repository (only `.cargo/audit.toml`), so no linker override and no compiler wrapper is configured; every measure below is unclaimed ground.

Separate target directories per agent or per stream remove the contention directly.
Cargo's lock is per build directory, and the standard remedy in the cargo issue tracker is exactly this isolation, with finer-grained locking still an open proposal ([cargo#15396](https://github.com/rust-lang/cargo/issues/15396), [cargo#6747](https://github.com/rust-lang/cargo/issues/6747)); the target directory is chosen by `CARGO_TARGET_DIR`, `build.target-dir` or `--target-dir` ([build cache](https://doc.rust-lang.org/cargo/reference/build-cache.html)).
The cost is disk: N agents multiply the 263 GiB, which makes the next two measures near-mandatory companions rather than optional.

sccache recovers most of the compilation that separate target directories would duplicate, and cargo's own documentation names it for this purpose: "A third party tool, sccache, can be used to share built dependencies across different workspaces" (same page).
It is enabled through `RUSTC_WRAPPER` or `build.rustc-wrapper`, and its documented caveats matter here: "Crates that invoke the system linker cannot be cached. This includes `bin`, `dylib`, `cdylib`, and `proc-macro` crates", and "Incrementally compiled crates cannot be cached" ([sccache](https://github.com/mozilla/sccache)).
The reading for this repository is to apply it to the check and CI-shaped lanes with `CARGO_INCREMENTAL=0`, and leave the inner loop on cargo incremental.
Backends include local disk, S3, Redis, GCS, WebDAV and a multi-level hierarchy, so a shared cache is available later without changing the local setup.

A faster linker is the single cheapest change.
mold reports that it "links 4.9x faster than LLVM lld and 1.9x faster than wild at the median", from a benchmark run on nine large programs with linkers built 2026-08-28, and documents the two-line `.cargo/config.toml` form ([mold](https://github.com/rui314/mold)).
Link time is paid per binary, and this workspace has many: `tam-storage` alone declares 26 cargo targets and `tam-api` 14 (measured, `cargo metadata`).

Profile tuning attacks both time and the 263 GiB.
The dev profile defaults to `debug = true`, meaning full debug info, and `test` inherits it; `"line-tables-only"` "generates the minimal amount of debug info for backtraces with filename/line number info", and `split-debuginfo` moves what remains out of the executable ([profiles](https://doc.rust-lang.org/cargo/reference/profiles.html)).
Backtraces keep working, and both the artefacts and the linker's input shrink.

Crane already does part of what Bazel promises, and one gap is visible in `flake.nix`.
`buildDepsOnly` builds against a dummy source so that "we do not need to rebuild the cargo artifacts derivation whenever the application source changes", and `cargoClippy` and `cargoNextest` both require and reuse that artefact, while `cargoFmt`, `cargoAudit` and `cargoDeny` set it to null because they do not need it ([crane API](https://crane.dev/API.html)).
Our flake follows that shape except for the `portable` check, which starts cold for five targets.
Building a per-target `buildDepsOnly` for those triples is a half-day change that removes the largest duplicated compile in the flake.

nextest partitioning is a real feature, `--partition slice:m/n` and `--partition hash:m/n` for splitting a suite across machines ([partitioning](https://nexte.st/docs/ci-features/partitioning/)), but it addresses a bottleneck this repository does not have: the pure suite runs 839 tests in under a second, and the database lanes are bound by Postgres rather than by test parallelism.

A Nix binary cache helps once a second machine exists.
attic is self-hostable with global deduplication over S3-compatible storage, and describes itself plainly as "an early prototype" ([attic](https://github.com/zhaofengli/attic)); cachix is the hosted equivalent.
The limit is granularity: a Nix cache stores whole derivation outputs, so any source edit invalidates each check derivation, where Bazel would invalidate only the affected crate actions.
That gap is the one pain the cheap list does not fully close, and it is the honest core of the case for Bazel.

Buck2 is the other monorepo build system and is not a shortcut.
Its README warns "rough terrain lies ahead", states there is no stable release tag, and says non-Meta users will "encounter quite a lot of rough edges right now" ([buck2](https://github.com/facebook/buck2)).
It would trade Bazel's larger ecosystem for a smaller one while asking for the same graph-authoring work.
For completeness, a third-party alternative to rules_rust exists, `hermeticbuild/rules_rs`, which claims to use "your Cargo lockfile directly, with no Cargo workspace splicing" plus first-class Windows toolchains, but it is at 0.0.x versions with 91 stars and depends on its own patched fork of rules_rust ([rules_rs](https://github.com/hermeticbuild/rules_rs)).

What Bazel would and would not subsume.
It subsumes sccache, the crane artefact reuse, and part of the Nix binary cache's job, because all three become one action cache.
It does not subsume the separate-output-base discipline, which it needs for the same reason cargo does.
It does not subsume the linker choice or the debuginfo settings, which apply to its rustc actions exactly as they apply to cargo's.
It does not subsume cargo at all for `sqlx prepare`, cargo-deny, cargo-audit, the Tauri bundle, or the cargo-xwin Windows path.

## 5. Verdict

Reject for now, and revisit only on a named trigger.

The reasoning is arithmetic rather than aesthetic.
The migration is 31 to 60 engineer-days for a solo founder whose current milestone plan is measured in weeks, it cannot replace cargo, it adds a second lockfile discipline and a 0.x upgrade treadmill, and its clearest benefit, cross-lane deduplication, is partly available for under two days of work through a linker swap, profile tuning, per-stream target directories and a per-target crane dependency artefact.
Against that, the inner loop that agents actually spend their time in would get slower, because Bazel does not use rustc's incremental compilation.
The enforcement layer is the specific risk that makes a partial migration worse than none: the founder-gated lint table is a cargo feature, and a Bazel build would keep compiling happily without it.

Conditions that would change the verdict, any one of them sufficient to re-open the question.
A second and third engineer sharing the repository, at which point remote cache hits are shared across people rather than across one person's lanes.
Real CI capacity beyond the flake, where remote execution and cross-run caching pay for the setup that a single laptop cannot amortise.
Polyglot growth: a third language, or cross-language code generation between Rust and TypeScript beyond today's `typegen` binary and wasm bridge, where cargo, npm and nix stop composing cleanly.
A split into many independently deployable artefacts with a deep shared dependency graph, which is the shape Bazel is actually designed for.

Recommended cheap sequence, in order, with the expected effect.

1. Set `[profile.dev] debug = "line-tables-only"` in the workspace `Cargo.toml`, and confirm backtraces still name files and lines. Hours; attacks the 263 GiB and link time.
2. Add `.cargo/config.toml` selecting mold for Linux, with mold added to the devshell beside the existing `pkgs.lld`. Hours; attacks every link in every lane.
3. Give each concurrent agent or stream its own `CARGO_TARGET_DIR`, and add sccache with a local disk cache and `CARGO_INCREMENTAL=0` for the check lanes only. Half a day; removes the lock contention without paying for it in recompiles.
4. Build a per-target `buildDepsOnly` for the five portable triples in `flake.nix`. Half to one day; removes the largest duplicated compile in `nix flake check`.
5. Measure again before anything else. The decisive numbers are cold and warm `just check`, `just check-portable` and `nix flake check`, before and after steps 1 to 4; a measurement run was in progress on another agent as this was written, and that data, not this document, should settle whether any further investment is warranted.
6. If and only if a trigger condition above fires, run a two-day spike limited to `crate_universe` plus the pure core crates, and use the observed cache-hit rate to price the rest.

## Open questions

1. Does the founder want the enforcement layer expressible in exactly one place? If yes, that is an argument against Bazel independent of speed, since `[workspace.lints]` and `clippy.toml` are cargo and clippy features and would need a parallel Bazel expression.
2. What is the actual measured cost today of `just check` cold and warm, and of `nix flake check`? Every estimate of Bazel's benefit here is a ratio against numbers that were not measured for this document.
3. How many agents genuinely build concurrently, and do they run the same lane? If they mostly run different lanes, per-stream target directories plus sccache close the gap; if they run the same lane on the same crates, a shared action cache is worth more.
4. Is a second machine or a CI runner on the roadmap within the next two milestones? That single fact moves both the Bazel case and the Nix-binary-cache case.
5. Is the desktop bundle expected to stay on the GitHub Windows runner (per D29), which would leave the Windows leg outside any Bazel graph regardless?

## Unverified

- Whether any rules_rust or crate_universe feature reads the cargo `[workspace.lints]` or `[lints]` tables for first-party targets; the conclusion that lints must be re-expressed as `rustc_flags` follows from Bazel composing its own rustc command line, but no documentation stating this was found.
