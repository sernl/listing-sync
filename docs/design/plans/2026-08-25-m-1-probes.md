# M-1 probes implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Run the M-1 probes that turn the design's largest open questions into cheap, recorded answers, and decide `tam-browser` versus a plain HTTP client and the create strategy before any product code is written.

**Architecture:** M-1 produces no production code. Each probe is either agent-executed against public surfaces, or a founder-executed capture on the founder's own authenticated Tes account followed by agent analysis of the saved artifact. Findings are recorded as working notes with evidence, and the milestone closes by folding the answers into the decision record.

**Tech Stack:** curl, ripgrep, jq, a browser's devtools (HAR export), shellcheck, a systemd user timer for the longevity logger. No Rust product crates are created.

## Global constraints

- Account safety is paramount and its tolerance is near-zero; a single suspension attributable to a probe is a milestone-level failure.
- Prefer read-only inspection; any test upload goes to a draft or is deleted immediately afterward, one at a time, watched, never left live.
- Never transcribe a marketplace vocabulary, phase label, or grade age-boundary from memory; every such value is captured from the live authenticated form and stored as data.
- Every finding records its egress (host and public IP), the account used, the method, and a path to the saved evidence, so a later reader can tell verified from inferred.
- Findings are working notes under `docs/notes/probes/`, one sentence per line, no product claims.
- Probe tooling lives under `probes/` and is outside the cargo workspace; shell scripts pass `shellcheck` before commit.
- Session cookies and any exported authenticated artifacts are secrets: they live under `probes/local/` which is gitignored, and are never committed.
- Commit recipe (jj colocated, signed): the working copy auto-snapshots, so `jj describe -m "<msg>"`, then `jj bookmark set main -r @`, then `jj new`, then `git push origin main`. Each task's final step gives the exact `<msg>`.

```bash
#!/usr/bin/env bash
# Re-probe marketplace egress reachability. Reusable whenever the host moves.
# Usage: probes/reachability.sh <url> [user-agent]
set -euo pipefail
url="${1:?usage: reachability.sh <url> [user-agent]}"
ua="${2:-curl/8.0}"
status="$(curl -sS -o /dev/null -w '%{http_code}' --max-time 25 -A "$ua" "$url" || echo 000)"
now="$(date -u +%Y-%m-%dT%H:%M:%SZ)"
printf '%s\t%s\t%s\t%s\n' "$url" "$status" "$ua" "$now"
```

### Task 3: Upload request-shape probe — browser versus HTTP client

[Founder capture -> agent analysis]

The highest-leverage hour in the plan. The answer decides whether `tam-browser` exists at all.

**Files:**
- Create: `docs/notes/probes/02-upload-request-shape.md`

**Interfaces:**
- Produces: a decision, `UploadTransport = { MultipartFormPost | JsMediatedChunked }`, that gates the `tam-browser` crate and the whole per-session isolation design.

- [ ] **Step 1 (founder): Capture the upload as a HAR**

On your own Tes author account, open the browser devtools Network tab with "Preserve log" enabled, begin creating one real resource with one small file, and proceed until immediately after the file upload and form submission complete.
Do not publish: leave it as a draft if a draft exists, otherwise stop before final publish, and delete the resource afterward if one was created.
Right-click the network log, "Save all as HAR", and save to `probes/local/tes-upload.har`.

- [ ] **Step 2 (agent): Identify the upload request(s)**

Run:
```bash
jq -r '.log.entries[]
  | select(.request.method=="POST" or .request.method=="PUT")
  | [.request.method, (.request.postData.mimeType // "-"), .request.url] | @tsv' \
  probes/local/tes-upload.har | sort -u
```
Expected: the upload endpoint(s) with their HTTP method and request MIME type.

- [ ] **Step 3 (agent): Classify the transport**

Run:
```bash
jq -r '.log.entries[]
  | select(.request.url | test("upload|resource|asset|file"; "i"))
  | { method:.request.method, mime:(.request.postData.mimeType // "-"),
      url:.request.url, status:.response.status,
      reqbytes:(.request.bodySize) }' probes/local/tes-upload.har
```
Decide: a single `POST` with `multipart/form-data` carrying the file is `MultipartFormPost`; many sequential chunk `PUT`/`POST` requests, or an `application/json` control channel plus separate binary parts, or a WebSocket, is `JsMediatedChunked`.

- [ ] **Step 4 (agent): Confirm the DOM has a real file input**

Ask the founder to run, in the devtools console on the upload page:
```javascript
document.querySelectorAll('input[type=file]').length
```
Record the count. A real `input[type=file]` is what a non-browser client cannot drive and what `send_keys`/`setFiles` needs.

- [ ] **Step 5 (agent): Record the finding and its consequence**

Create `docs/notes/probes/02-upload-request-shape.md` from the template.
State the transport, and the consequence: `MultipartFormPost` deletes `tam-browser`, the per-session isolation, the shared-memory work and the forced browser-upgrade cadence, and drops the dominant infrastructure cost line by roughly thirty times; `JsMediatedChunked` makes the browser mandatory and every one of those costs real.

- [ ] **Step 6: Commit**

Commit per the recipe with msg: `docs(probes): Tes upload request-shape — browser vs HTTP client`

### Task 9: Session-longevity logger

[Agent-writes tooling; founder provides cookie and runs it over weeks]

Session longevity is undocumented on Tes and sets the parking TTL, the pre-flight cadence, and whether sync can ever be described as unattended. This task starts the multi-week observation early.

**Files:**
- Create: `probes/session-longevity.sh`
- Create: `probes/session-longevity.timer.example`, `probes/session-longevity.service.example`
- Create: `docs/notes/probes/08-session-longevity.md` (opened now, completed after the observation window)

**Interfaces:**
- Consumes: a session cookie the founder exports to `probes/local/tes-cookie.txt` (gitignored).
- Produces: an append-only log `probes/local/session-longevity.log` of `iso8601<TAB>http_status<TAB>authed|challenged|expired`, and, after weeks, the observed session lifetime and whether an OTP re-challenge appears.

- [ ] **Step 1: Write the logger**

Create `probes/session-longevity.sh`:

```bash
#!/usr/bin/env bash
# Poll an authenticated Tes endpoint and classify session state over time.
# Requires probes/local/tes-cookie.txt (Netscape or "Cookie:" header line).
set -euo pipefail
here="$(cd "$(dirname "$0")" && pwd)"
cookie_file="$here/local/tes-cookie.txt"
log="$here/local/session-longevity.log"
probe_url="${TES_PROBE_URL:-https://www.tes.com/my-tes}"
[ -f "$cookie_file" ] || { echo "missing $cookie_file" >&2; exit 1; }
code="$(curl -sS -o /dev/null -w '%{http_code}' --max-time 25 \
  -H "Cookie: $(cat "$cookie_file")" -A "Mozilla/5.0" "$probe_url" || echo 000)"
eff="$(curl -sS -o /dev/null -w '%{url_effective}' --max-time 25 -L \
  -H "Cookie: $(cat "$cookie_file")" -A "Mozilla/5.0" "$probe_url" || echo "")"
state="authed"
case "$code" in 401|403) state="expired";; esac
case "$eff" in *login*|*sign-in*|*otp*) state="challenged";; esac
printf '%s\t%s\t%s\n' "$(date -u +%Y-%m-%dT%H:%M:%SZ)" "$code" "$state" | tee -a "$log"
```

- [ ] **Step 2: Lint the logger**

Run: `shellcheck probes/session-longevity.sh`
Expected: no output, exit 0.

- [ ] **Step 3: Write the systemd user timer examples**

Create `probes/session-longevity.service.example`:

```ini
[Unit]
Description=Tes session-longevity probe
[Service]
Type=oneshot
ExecStart=%h/projects/edtech-workspace/listing-sync/probes/session-longevity.sh
```

Create `probes/session-longevity.timer.example`:

```ini
[Unit]
Description=Run the Tes session-longevity probe hourly
[Timer]
OnCalendar=hourly
Persistent=true
[Install]
WantedBy=timers.target
```

- [ ] **Step 4 (founder): Provide the cookie and start the timer**

Export the Tes session cookie from your logged-in browser into `probes/local/tes-cookie.txt`, then install and start the user timer:
```bash
cp probes/session-longevity.service.example ~/.config/systemd/user/tes-longevity.service
cp probes/session-longevity.timer.example   ~/.config/systemd/user/tes-longevity.timer
systemctl --user daemon-reload
systemctl --user enable --now tes-longevity.timer
```

- [ ] **Step 5: Verify one manual run logs a row**

Run: `probes/session-longevity.sh && tail -1 probes/local/session-longevity.log`
Expected: one TSV row with a status and `authed` while the session is fresh.

- [ ] **Step 6: Open the finding, to be completed later**

Create `docs/notes/probes/08-session-longevity.md` from the template, stating the method and that the observed lifetime and any OTP re-challenge cadence land after the multi-week window; until then the product describes sync as scheduled and supervised, not unattended.
