# The web stack, and Android second

This document holds the client technology choices the design specification summarises in a paragraph and does not reproduce.
The client performs no automation, so nothing here is load-bearing for correctness; it is load-bearing for build cost, for whether an agent can hold the front end in context, and for whether the interruption flow reaches a seller's phone.

React and TypeScript are settled, and the reasoning against a Rust front end is worth carrying because it will be re-litigated: Leptos's creator posted on 2026-05-08 that Leptos "is not abandoned but will be lightly maintained going forward"; the shadcn/ui port and its Radix headless-primitives dependency were both archived on 2026-02-02, twenty-two minutes apart, leaving no maintained accessibility-behaviour layer; thaw's Leptos-0.8 support has sat at `0.5.0-beta` for fifteen months; and cargo-leptos does not support CSR builds, so a second toolchain and a `wasm-bindgen-cli` exact-version pin enter the Nix build.

| Concern | Choice | Reason |
|---|---|---|
| Build tool | Vite 8.2.2 | Standard for a React SPA; produces a static directory axum can serve |
| Router | TanStack Router 1.170.32 | Typed routes and typed search params, the agent-legible option |
| Server state | TanStack Query 5.102.2 | The snapshot-plus-delta model is expressed in its cache primitives |
| Components | shadcn/ui on Tailwind 4.3.3 | The code lands in the repository rather than behind a dependency |
| Toasts | `sonner` | shadcn's `toast` is deprecated |
| Table and virtualisation | TanStack Table 9.1.2, TanStack Virtual 3.14.10 | Headless row model, required at catalogue scale |
| Forms | react-hook-form 7.86.0 with zod 4.4.3 | Deliberate deviation from the house TanStack Form preference |

The forms deviation is stated rather than silent: shadcn's `Form` component is wired to react-hook-form, the product has few forms, and re-wiring shadcn's primitives to satisfy a preference would cost more than the preference is worth here.
Query fetches the snapshot and a single effect-owned `EventSource` merges deltas via `queryClient.setQueryData`; the experimental `streamedQuery` is not used, because its chunk-accumulation semantics model a token stream rather than a mutable projection, which is the wrong shape for a progress tree whose nodes change state rather than append.
One flake, one repository, two vendoring mechanisms with the same shape: Rust dependencies vendored by crane's `vendorCargoDeps` from `Cargo.lock`, npm dependencies vendored by `importNpmLock`, which needs no hash because it relies on the integrity hashes already in `package-lock.json`, so neither side requires a hash a human must remember to update and both fail the build rather than drifting.
Serve the built UI from a runtime path via `ServeDir(...).not_found_service(...)` rather than embedding it in the binary, so a UI change never invalidates crane's `cargoArtifacts` and a CSS tweak does not trigger a full Rust rebuild, which matters more than it sounds for an agent-driven build where a ten-minute rebuild per iteration is what causes an agent to start bypassing the build.
Two generators keep the domain vocabulary from drifting: `ts-rs` 12.0.1 emits TypeScript from `tam-types`, where `Outcome`, `FailureCode`, `ItemOutcome` and `JobEventKind` live, and `openapi-typescript` 7.13.0 over the OpenAPI 3.1 document produced by `utoipa` 5.5.0 with `utoipa-axum` 0.2.0 covers routes, request shapes and status codes that `ts-rs` cannot see.
Two caveats carry forward — `utoipa-axum` 0.2.0 has not been released since January 2025 so verify it builds against axum 0.8.9 before committing to it, and `utoipa` emits OpenAPI 3.1.0 only — and `ts-rs` was verified at 12.0.1 but was not put through the maintenance audit the browser crates received, so there is no bus-factor or release-cadence finding to report and none should be invented.
The generator earns its place on one condition that changes the answer if unmet: generated output must be checked for freshness in `nix flake check` and must fail the build when stale, because a generator whose output is committed and allowed to drift manufactures the appearance of a shared vocabulary while the two sides diverge.

The mobile question reduces to reach, push and build cost rather than capability, and the recommendation is an installable PWA with a service worker and Web Push.
Tauri v2 is the option the Rust mandate would otherwise select and it is disqualified on the one capability that justifies a mobile client at all, because its notification plugin documents only local notifications with no FCM or APNs path and push is the entire reason a phone client exists here; round one's separate finding that Tauri mobile cannot host automation is irrelevant under this architecture and should not be mistaken for the reason.
Nix buildability rules out every native option equally rather than discriminating between them, because Android builds under Nix are actively broken since the Android SDK manager expects a writable directory against a read-only store, and iOS requires Xcode which is not packaged, so any native artifact requires a second non-Nix pipeline that breaks the self-hosted-NixOS-only premise.
The costs are specific: no Play Store listing and so no store search surface or store-mediated trust signal, no reliable iOS push so iPhone users get the responsive web client and the interruption flow degrades to email, and Add-to-Home-Screen must be taught in onboarding rather than assumed.
One further cost is conditional rather than settled, and the third drafter stated it unconditionally: under the current `StoredCredential` model a re-link is a form the phone can complete, and the desktop-only constraint arrives only if the `SellerDrivenSession` courier variant is later adopted, because the courier runs on the seller's own machine and has no Android counterpart, at which point a phone can relay a `ParkedLive` code and cannot complete a `ParkedCold` re-link and onboarding copy must say so.
If a Play Store listing is later forced the ranked fallbacks are a Trusted Web Activity over the same PWA, then Capacitor, then React Native, then Kotlin with Compose, all four inheriting Google Play's API-36 target requirement that took effect 31 August 2026 and roughly a week a year of target-SDK maintenance on top of the second build pipeline; whether a listing is required is an open question the research flags and does not answer, closed by asking three Tes authors before spending anything on Android.
